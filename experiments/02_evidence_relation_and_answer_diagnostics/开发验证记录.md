# 实验 02：开发验证记录

## 关系判断

`src/relation.py` 将两条用户原文作为输入，输出关系及引用位置，并依据身份、范围、支持和显式变化/纠正的模型建议进行保守路由。它没有事实库检索，没有有效时间计算，模型布尔值并非真实的独立语义验证；动作都是 `_PROPOSED` 或 DEFER，`applied=false`，不写状态。模型不得看到 `fixtures/development_expected_v2.json`；其期望是为开发案例自拟的暂定标签，并非人工独立评审的标准答案。

初次运行中，模型把“旧陈述目前不再有效”混成“旧原文没有陈述该内容”，导致明确搬家与纠正错误暂缓；提示词澄清支持指陈述是否出现在各自原文，而非是否仍为当前或客观真相。另将“旧住址结束但未说新住址”改为 `RETIRE_OLD_PROPOSED` 而不是创造新的住址值，保留首轮结果。最终运行 `runs/01_relationship_development_final_20261101/`：10 条解析，和暂定开发期望关系一致 9/10，动作落在允许范围 10/10。`relative` 将用户与姐姐的职业标为 COMPLEMENT，而期望是 COEXIST/UNCERTAIN；因主体不同该候选动作仍为 DEFER。`development_diagnostic.json` 列明分母、每条结果与允许的多种动作；这不是准确率或性能结论。

## 回答导向诊断

`src/reader.py` 使用相同两条原文和问题，比较仅提供原文与额外提供模型生成关系建议的回答；候选问题输入在 `fixtures/answer_development_inputs.json`，期待仅供事后核查，不进入模型。两种模式均是使用同一 qwen3.8-flash 的自拟提示，并非 LiCoMemory 原始系统基线。关系模式使用同一个模型的建议；可能继承其偏差。

`runs/02_answer_development_comparison_20261101/` 的五道构造问题及两种模式均返回可解析回答，引用 ID 可在输入中找到（不是引用语义核验）。按本次开发者对五个简单案例的非独立事后检查，两组均回答了预设的核心信息：搬家后上海、之前北京、纠正后 3 只猫、两条不同住址不足以推断当前住址、不再住北京但当前住处未知。不能因此称两组各有 100% 真实准确率或关系模块改善了回答。样本小且同一开发者设计样本/期望，不能代替正式评测和独立标注。计划后续在真实数据、时间可确定和人工审查的独立测试集上比较当前/历史/变化问题，记录误更新、误拒和成本。

所有来源、响应、审查、输出及输入代码哈希位于各运行目录；没有传入数据集标准答案，没有写入有效记忆。第一次和修改后运行分别保留；重放须使用对应 manifest 的代码。
