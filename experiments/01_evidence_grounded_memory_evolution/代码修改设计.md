# 实验 01：代码修改设计

**状态：设计草案；尚未实现。**  
**项目：** `/home/cwf/Code/LiCoMemory-main`；旁边的 `LiCoMemory` 是独立项目，不能直接视为本项目实现。  
**目标：** 面向个人长期对话中的明确生活事实，通过原文支持、关系判断与更新门控维护可追溯状态，并在回答时区分当前、历史和不确定信息。

## 1. 当前代码与设计范围

- `coregraph/graph_rag_core.py::GraphRAGCore.insert` 组织建图；`coregraph/dynamic_memory.py` 负责构图、增量摄取、Chunk 与 pickle 持久化。
- `coregraph/graph_builder.py` 使用 `networkx.DiGraph`；相同端点的独立关系可能不能完整保留。`chunking/chunk_processor.py::process_corpus` 每次从 0 分配 Chunk ID；在增量摄取中需要避免来源覆盖。
- `query/query_processor.py::_process_unified_query` 执行实体、三元组、摘要和 Chunk 检索后生成回答；现有流程不等同于依据原文提交状态变更或验证回答引用。
- 一道 LongMemEval 开发题显示新旧证据均被传入回答但回答采用旧值；这只是一条诊断，不证明具体错误根因或总体效果。

**方案边界：** 保留原始图作为关联/召回索引，独立保存事实出现、证据、状态版本和决策；默认关闭新流程。暂不引入数据库，不以图节点或相似度作为事实正确性的证明。

## 2. 不可变来源与存储对象

所有标识在数据集、对话、会话、轮次和用户范围内明确；同一次处理可重放，跨会话不会覆盖。原始说话人及文本必须保留，原始字段与语义归一结果分开。

| 对象 | 最少字段 | 责任 |
|---|---|---|
| Evidence | `evidence_id`, `dataset_id`, `conversation_id`, `session_id`, `turn_id`, `speaker`, 原文、可核对的片段位置、`known_at` | 保存来源，不用摘要替代原文；引用可回到具体轮次 |
| FactOccurrence | `fact_id`, `evidence_ids`, `subject`, 原始 predicate/value, derived attribute/value, scope, modality, event_time, extraction_status | 一次带来源的陈述；相同事实的不同来源仍各自保留 |
| StateVersion | `state_id`, identity/attribute/scope, value, modality, valid time、known time、status、supporting fact IDs | 表示某个时间和范围内系统接受的状态；未知时间与开放区间分别表达 |
| EvolutionDecision | `decision_id`, 新旧 ID, relation, action, evidence IDs, reasons, input_known_at, policy_version, applied, revision | 保存候选、审查、实际提交与失败/暂缓原因 |
| AnswerClaim | claim、引用 Evidence ID、关联状态版本、校验结果 | 将回答主张与证据关联；检查失败仍可保留原始草稿供审计 |

会话时间与事实生效时间分别记录；未知不填成确定值。用户声明支持的是“对话中用户这样说过”，不是对现实真相的绝对保证。原文引用须核对片段与实际来源，引用存在不自动等于语义支持。

## 3. 拟新增的模块与接口

以下是拟议文件/接口，不是已经存在的能力。根据实现需要可以合并文件，但对外责任应保持不变。

| 文件 | 拟议接口 | 职责 |
|---|---|---|
| `coregraph/evidence_store.py` | `put_source(source) -> evidence_id`; `get(evidence_id)` | 来源、稳定 ID、原文片段与存在性校验；拒绝冲突复写 |
| `coregraph/fact_store.py` | `append(fact) -> fact_id`; `get(fact_id)` | 保留每次来源事实及原始谓词和值，维护可重建的主体/属性索引 |
| `coregraph/affected_memory_retriever.py` | `retrieve(new_fact, *, known_at, k) -> candidates` | 结构与语义召回并记录路径；相似只是候选，不作为证据或更新授权 |
| `coregraph/evidence_relation_judge.py` | `judge(new_fact, old_fact, evidence) -> relation_proposal` | 提出 duplicate/support/complement/change/correction/conflict/uncertain，记录引用及理由 |
| `coregraph/update_policy.py` | `decide(proposal, context) -> decision` | 独立检查身份、范围、时间、模态、证据支持和动作充分性，输出 ADD/MERGE/REPLACE/CORRECT/RETAIN/DEFER |
| `coregraph/state_store.py` | `commit(decision, *, expected_revision, idempotency_key) -> result`; `read(subject, attribute, *, known_at, valid_at)` | 状态、决策、版本与审计保存；重放幂等、版本校验、一致提交 |
| `coregraph/evolution_pipeline.py` | `process_source(source, *, mode) -> trace` | 串联事实抽取、验证、召回、关系、策略和版本提交；逐阶段记录失败及耗时 |
| `query/state_aware_retriever.py` | `retrieve(question, *, known_at, valid_at) -> evidence_bundle` | 面向当前/历史/变化问题取状态及原始依据；所有可见数据统一时间截止 |
| `query/answer_verifier.py` | `verify(answer_claims, evidence_bundle) -> checks` | 检查引用存在、主张支持、时间与不确定性；模型判定不是形式化真值证明 |

**隔离：** 构图、召回、关系判断、更新策略、回答和验证器都不得读取 gold answer、gold evidence、MemConflict 隐藏档案及答案会话标注。评测器单独读取 gold。来源存在、事实支持、关系成立、更新充分是四个不同检查；不使用同一个相似度/置信度代替。

## 4. 写入路径与门控

1. 接收原始对话，先保存可追溯来源；为事实候选保存来源指针、说话人、抽取原文与不确定性。
2. 检查引用是否存在、主体/范围/模态是否被原文支持；不支持或无法确定的候选进入 `review_queue` / `skipped_candidates`，不进入有效状态。
3. 对通过来源检查的候选，召回可能受影响旧事实；记录候选数量、排序和路径，不把候选边当作已证实事实。
4. 比较主体身份、属性含义、属性是否多值、范围、时间和模态，给出关系建议及证据引用。
5. 策略层独立判断动作：明确时间变化可提出 REPLACE；明确纠正可提出 CORRECT；同一属性可多值、不同主体或不同范围可并存；计划/否定/不确定信息不能伪装为已发生的精确状态；不充分时 DEFER。
6. `active` 提交须验证 decision_id、完整输入引用与 `known_at`、旧状态修订号、幂等键和事实/来源一致性；原子写入决策、版本及索引状态。失败必须保留原因，不能只写一半。

近似案例：1250 是较早的明确陈述，“认为接近 1300”是较新的近似、不确定陈述；可以登记这一陈述及时间，不能将 1300 写成确定精确值。实际是否提交状态、保留何种并存关系，须由已定义规则和证据检查决定，不预设因为时间晚就替换。

## 5. 查询路径与时间

查询解析输出 `known_at`（截至何时系统可见）和 `valid_at`（问题询问的有效时间），两者可不同；缺失或模糊时保留未知及时间精度。历史查询中，所有参与决策的事实、原文、状态、图索引及摘要必须受统一可见性约束；不能通过召回 Chunk 或摘要绕过截止时间。未知 `valid_to` 不自动等于永远有效。

按问题构造 evidence bundle：问题时间及状态视图、适用状态、相关旧版本、决策、原文及 unresolved 标记。当前、历史、变化原因使用不同证据；答案缺少支持时说明不确定。先生成草稿，后做 claim/引用/时间/近似程度检查；回答侧提出的重新审查请求不得绕过写入策略直接改状态。

## 7. off / shadow / active 的边界

- `off`：不调用新抽取/决策，不改变原有输入、图、排序、缓存、回答或随机参数；以固定输入和服务响应比较基线路径，记录必要的接口适配差异。
- `shadow`：抽取、判断并记录候选和拟议决策；`applied=false`，不得修改有效状态或影响原始检索排名。
- `active`：只有经门控的决策才提交；支持同一输入重放不重复提交，修订冲突不提交，审计及状态一致。

自动运行不得以 embedding 相似度、模型自评置信度或标准答案单独授权更新；模型和 verifier 也可能出错。状态提交目标应具体且唯一，否则暂缓。

不直接覆盖现有基线图和预检结果。由于服务器目录不是 Git 仓库，实施时先在实验 01 中准备独立代码快照并记录源文件哈希；实验使用隔离的数据/输出目录。保存 schema 版本、代码/配置/模型版本及输入哈希。单个提交通过临时文件、校验和原子替换；跨文件版本、状态、索引必须有一致快照或可重放提交日志，崩溃不得混合不同 revision。

## 9. 实施顺序及验收

1. **证据底座：** 构建稳定 ID、原文/说话人定位与独立事实；验收跨会话不覆盖、平行关系与独立来源不丢失、旧图不可恢复部分被明确标记。
2. **影子演化：** 事实支持、候选召回、关系建议、门控及 trace；验收 unsupported 不写入、候选不等于证明、`applied=false` 且基线结果不变。
3. **受控提交：** 版本与事务；验收变化/纠正/多值/计划/否定/主体范围混淆、同一决策重复提交、修订冲突、崩溃恢复。
4. **状态感知问答：** 同时检查状态与原文在 known_at/valid_at 的可见性，覆盖未来信息、时间未知、近似值及冲突；验证引用存在与语义支持分开记录。
5. **实验：** 先受控案例，再冻结的开发预检、独立测试；对比原始 LiCoMemory、时间优先、回答时冲突处理及完整方法，在相同模型/输入/预算下记录答案、检索、更新、失败和成本。

受控测试先于修改写出并观察失败，再实现并复验；公开数据 gold 只用于事后评测。模型代理评估单列，少量人工复核需标注分母与分歧；不得将 10 条构造案例或单题预检当作准确率证明。
