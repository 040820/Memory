# 实验 01：候选事实语义审查规则 V2

**状态：设计规范，尚未接入代码或模型；不能用于声称已有实验效果。**

## 1. 目标与边界

对个人长期对话中抽取的候选，检查原文是否足以支持该候选，并保留可以复核的依据。V2 只审查单个候选，不判断两个事实之间是否发生变化，不授权记忆提交；即使审查为 `SUPPORTED`，也只能进入下一阶段。用户陈述证明的是“用户在对话中这样说过”，不等于现实真相已被证实。

审查对象是带限定条件的完整主张：**主体 + 属性/关系 + 值 + 极性 + 时间 + 模态 + 适用范围**。任何关键要素被改变、缺失或无法由上下文确定，不能仅凭某段原文出现类似词语判为支持。

审查输入只包含：目标用户的真实对话原文、原说话人、证据 ID、目标轮次的位置及必要的可见上下文，以及待审查候选。上下文必须带原始说话人和证据 ID，不得混入评测标准答案、答案来源标签或未来轮次。允许使用可见的相邻上下文解决代词与省略，但模型不能将助手的猜测当作用户确认。单轮无法判断主体时返回未知。

## 2. 审查步骤

1. **核验来源**：证据存在，候选引用是该来源中的连续原文，引用位置可复算；说话人和时间来源可追溯。定位失败不得进入语义支持判断，标记技术或来源失败并暂缓。
2. **识别原文实际主张**：按原文单独标注谁、什么属性、什么值、肯定/否定、时间、模态和范围；不要先假设候选正确。不能确认时保留未知。
3. **比较完整候选**：逐维对照主体、关系、值、极性、时间、模态和范围。数字、单位、近似程度和否定词不得省略；推测、计划不得提升为已发生。
4. **判定支持关系**：基于允许使用的原文与上下文，输出 `SUPPORTED`、`CONTRADICTED` 或 `INSUFFICIENT`，并给出确切依据。不得以引用存在、时间新、向量相似度或自报置信度代替语义支持。
5. **独立应用路由规则**：检查格式、来源、关键字段和判断间是否存在可机器判定的冲突；不能确定则暂缓。结果写审查记录，`applied=false`。

## 3. 输出字段与允许值

下表规定目标语义。`UNKNOWN` 是信息不足而不是否定，也不必强制猜测；一个事实可以同时有时间、模态、极性和不确定性。

| 字段 | 允许值 | 定义 |
|---|---|---|
| `source_check` | `PASS`, `FAIL`, `UNKNOWN` | 原文、证据 ID、引文及位置是否可核对。只说明来源可定位。 |
| `source_subject` | `USER`, `OTHER`, `MULTIPLE`, `UNKNOWN` | 原文中被描述属性实际归属的对象；不是候选整体是否正确。若为他人，补 `subject_reference` 原文片段；`MULTIPLE` 不自动等同 USER。 |
| `candidate_subject_match` | `MATCH`, `MISMATCH`, `UNKNOWN` | 候选主体与原文对象是否相同；仅有“姐姐是教师”不能证明“用户是教师”。 |
| `time_reference` | `PAST`, `PRESENT`, `FUTURE`, `UNSPECIFIED` | 原文所指事实时间，不等同会话时间；混合时间或粒度不明时保留原文时间片段和未知。 |
| `modality` | `ASSERTED`, `PLAN`, `HYPOTHETICAL`, `POSSIBLE`, `UNKNOWN` | 已明确陈述、意图/计划、假设、可能或未知。对于包含多种模态的复合语句，拆候选；拆不开为 UNKNOWN。`ASSERTED` 可是过去事件，不等于当前状态。 |
| `polarity` | `POSITIVE`, `NEGATIVE`, `UNKNOWN` | 对审查中的属性和值是肯定还是否定。例如“不住北京”对“住北京”为 NEGATIVE。否定计划不等于否定计划中的事件。 |
| `precision` | `EXACT`, `APPROXIMATE`, `UNKNOWN`, `NOT_APPLICABLE` | 对数字/日期等值是否精确；没有标度或不适用的事实使用 NOT_APPLICABLE。近似词、单位及原文保留。 |
| `scope_match` | `MATCH`, `MISMATCH`, `UNKNOWN` | 候选的属性含义、单位、对象、适用范围和时间语境能否与原文对齐；属性边界不清时 UNKNOWN。 |
| `semantic_support` | `SUPPORTED`, `CONTRADICTED`, `INSUFFICIENT` | 对**完整候选**的支持关系，定义见第 4 节。无法审查时用 INSUFFICIENT 并记录原因。 |
| `evidence_spans` | 列表 | 每项包含 `evidence_id`、`start`、`end`、`quote`；位置按原始 Python Unicode 字符索引，左闭右开；精确匹配并保留所有歧义。 |
| `reason_codes` | 列表 | 可多选，如 `SUBJECT_MISMATCH`, `QUOTE_NOT_FOUND`, `PLAN_AS_CURRENT`, `NEGATION_MISMATCH`, `SCOPE_UNCLEAR`, `TEMPORAL_UNKNOWN`, `MODALITY_UNKNOWN`, `NUMERIC_PRECISION_LOSS`, `MODEL_OUTPUT_INCONSISTENT`。 |
| `reason` | 字符串 | 引用证据并说明哪些要素支持或不支持，不能代替结构化字段或人工核查。 |
| `route` | `REVIEW_NEXT`, `DEFER`, `TECHNICAL_ERROR` | `REVIEW_NEXT` 仅表示允许进入后续旧记忆关系审查；不等于可信事实或可提交。 |
| `applied` | 固定 `false` | 本阶段不改状态、不执行更新。 |

除非引用能唯一定位，否则须记录所有匹配区间或明确指定可核对的区间，不得静默选第一处。多轮证据要分别列出各自 ID 和位置；没有证据时不要伪造引用。对于候选主张含相对时间，保留原词与会话时间的原始字符串、精度和时区；在基准不确定时不生成精确日期。

## 4. 三种语义关系的判定

- **SUPPORTED**：可见原文在主体、属性、值、极性、时间、模态和相关范围上足以支持完整候选；不需要猜测缺失要素。保留原文的不确定、近似和时间限定。原文“我计划搬家”能支持“我有搬家计划”，不能支持“我已经搬家”。
- **CONTRADICTED**：同一主体、同一属性/范围、同一时间及模态下，原文明确否定候选或陈述不可同时成立的事实。例如“我现在不住北京”与“我现在住北京”。先核对属性是否单值：不同时间、不同范围或可多值的两个陈述不自动矛盾。
- **INSUFFICIENT**：原文没有足够证据支持或明确否定候选，包括缺少主体、含义不清、时间未知、引用只证明相关主题、计划推当前事实、涉及他人却推断用户、值或数字表述范围不明确。证据不足不是反证。

“姐姐是教师”与“用户是教师”是主体不匹配且证据不足，并不自动逻辑矛盾：用户也可能是教师。只有原文同时明确“我不是教师”等，才有依据判为矛盾。对明显将他人事实错误归给用户的候选仍应 DEFER，而不是把 DEFER 的理由叫作已证实矛盾。

若上下文既包含支持也包含反对，且时间、指代或范围无法协调，记录所有可见依据并 `INSUFFICIENT`/`DEFER`；不能选择最新片段强行合并。它可能是后续关系审查的问题，不在本模块直接更新。

## 5. 路由规则（确定性、顺序执行）

| 优先级 | 条件 | 路由及说明 |
|---|---|---|
| R0 | 服务/解析错误、必需结构缺失、非法枚举或系统无法读取证据 | `TECHNICAL_ERROR`；单列技术失败，保留原始响应；不得计为模型语义拒绝。 |
| R1 | 引文不存在、来源 ID 不匹配、位置无法复核或引用非允许上下文 | `DEFER`；记录来源问题，不把候选存为有效事实。 |
| R2 | 原文属性主体不是目标用户、主体关系未知，或候选主体不匹配 | `DEFER`；保留候选与不确定信息。候选是“用户的姐姐是教师”属于不同主体/关系建模问题，不能简单把所有包含亲属的陈述丢弃。 |
| R3 | 完整候选不是 SUPPORTED，或关键范围/时间/模态无法与候选对齐 | `DEFER`；说明矛盾、证据不足或未知的具体维度。 |
| R4 | 可机械检查的结构字段与证据/其他字段不一致 | `DEFER`；例如标注精确原文引用却找不到该片段，或宣称证据为他人且主体匹配用户但无关系说明。不得仅凭字符串匹配自由文本推断推理正确。 |
| R5 | 计划、假设、可能或否定被候选改成已发生、确定的肯定事实 | `DEFER`；若候选本身准确表示“用户有计划/可能/否定”，可以作为相应限定的陈述进入后续审查，但不得转换为当前已发生状态。 |
| R6 | 通过以上检查，完整候选受支持，且保留时间、极性、范围和模态限定 | `REVIEW_NEXT`，`applied=false`；过去事实只作带时间限定的候选，不自动视作当前。 |

上述规则是**提议**，需根据实现中结构字段细化确定性条件和互斥优先级。多个原因同时出现应全部保留，不因首个失败丢失其他原因。是否能收集后续检查所需信息与技术失败要分开；不得因为无法解析就默默跳过并计入语义正确。

`REVIEW_NEXT` 之后仍需单独检查新旧记忆身份、属性、范围、单值/多值、时间、支持证据及更新充分性，并采用版本、幂等及事务门控。模型审查同意、引用可定位或新事实较晚，均不单独授权 `REPLACE` / `CORRECT`。更早事实应保留证据和版本，历史可见性同时受 known_at 与 valid_at 约束，未知有效结束时间不表示无限有效。

## 6. 案例对照

| 原文 | 候选 | 关键判断 | 语义 / 路由 |
|---|---|---|---|
| 我住在北京。 | 用户当前住北京 | 主体 USER，PRESENT，ASSERTED，POSITIVE；若当前语境可确定 | SUPPORTED / REVIEW_NEXT |
| 我计划明年搬到上海。 | 用户现在住上海 | USER，FUTURE，PLAN；计划不能证明当前居住地 | INSUFFICIENT / DEFER |
| 我计划明年搬到上海。 | 用户计划明年搬到上海 | 内容包含计划和时间限定 | SUPPORTED / REVIEW_NEXT；不能写成已搬家 |
| 我姐姐是教师。 | 用户是教师 | 原文对象 OTHER，候选主体不匹配；不排除用户也从教 | INSUFFICIENT / DEFER |
| 我姐姐是教师。 | 用户有一位姐姐，姐姐是教师 | 候选关系主体及语义与原文对齐 | 可 SUPPORTED / REVIEW_NEXT；需正确表达关系 |
| 我现在不住北京。 | 用户现在住北京 | 同一主体、范围和时间，极性相反 | CONTRADICTED / DEFER |
| 我 2020 年住在北京。 | 用户 2020 年住北京 | PAST，ASSERTED；保存 2020 年精度 | SUPPORTED / REVIEW_NEXT；不是当前状态 |
| 餐桌超过四人很难坐下。 | 餐桌最多只能坐四人 | “难”不等于“不可能” | INSUFFICIENT / DEFER |
| 餐桌最多坐四人。 | 餐桌最多坐六人 | 仅当相同含义、单位、范围和时点明确时 | CONTRADICTED / DEFER |
| 我可能以后搬到上海。 | 用户当前住上海 | POSSIBLE、时间未来/未指定 | INSUFFICIENT / DEFER |
| 我大约有 1250 本书。 | 用户恰有 1250 本书 | 精度丢失 | INSUFFICIENT / DEFER |
| 我现在住北京。 | 用户 2025 年住北京 | 未知当前对话时间或无法对齐具体年份 | INSUFFICIENT / DEFER |

## 8. 验证计划与通过条件

- 测试来源 ID、引用存在和字符区间、重复片段、错误 speaker、未来上下文、缺失时间与不同时间精度；每个技术失败都能单独计数。
- 按主体、极性、计划/可能、相对时间、单值/多值、数量精度及范围设计正反例和歧义例。修订原有控制标签时创建 V2 文件，保留 V1 结果及其标签，不回写原运行。
- 对有歧义的标签标记待复核而不是当作标准答案；独立人工核查一部分真实候选，报告分母和分歧。开发案例与冻结盲测分开；不得用盲测标签反复调提示。
- 在完全一致的 V2 输入、提示、规则及数据范围下比较线上模型和本地模型；分别报告每字段、完整候选支持、可复核引用、技术错误、DEFER 与误拒，和成本及耗时。不同模型供应商可能有不同输出和 token 统计，需如实记录。
- 通过程序验证和人工抽查之前，V2 不得接到自动状态提交；该阶段的任何数字都不证明 CCF-B 水准或论文贡献。
